# LLM Wiki 使用說明

> 使用者指南 · 資料夾指南 · 工作流程  
> Warren 的 AI 知識管理系統

---

## 1  這個系統是什麼？

LLM Wiki 是一個「讓 AI 幫你維護知識庫」的系統，概念來自 Andrej Karpathy 的 LLM Wiki Pattern。你負責策展方向與提問，AI（Claude）負責閱讀、摘要、整理、維護交叉連結。

**核心原則：** 知識必須被蒸餾才能進主知識庫。隨手記的東西先進 inbox，整理過才升級進 wiki。

**知識成熟度管道（單向流）：**
```
inbox/  →  raw/ 或 projects/  →  wiki/（蒸餾後）
```

### 系統的兩種用途

| 用途 | 你做什麼 | Wiki 扮演的角色 | 頁面寫法 |
|------|---------|----------------|---------|
| 累積知識 | 問問題、理解概念 | LLM 讀 Wiki 後回答 | 描述性：這是什麼、為什麼 |
| 執行任務 | 說「執行 [playbook]」 | LLM 讀 Playbook 後照步驟做 | 指令性：Step 1 做什麼、輸出是什麼 |

---

## 2  三層知識架構

Wiki 頁面分三個層次，區別在於**用途**，不是主題：

| 層次 | 資料夾 | 寫法 | 目的 |
|------|--------|------|------|
| ① 知識層 | `concepts/` `tools/` `marketing/`（知識類） | **描述性**：這是什麼、為什麼 | 理解、教學、查詢 |
| ② Skill 層 | `ai-workflow/` `marketing/`（SOP 類） | **指令性**：Step 1 做什麼、輸出是什麼 | LLM 執行單一可重複操作 |
| ③ Playbook 層 | `playbooks/` | **指令性**：串聯多個 Skill，有明確輸入輸出 | LLM 執行完整多步驟流程 |

**判斷這一頁屬於哪一層：**
- 在「解釋一個概念/工具/方法是什麼」→ 知識層
- 在「說明如何執行一個操作（Step 1, 2, 3）」→ Skill 層
- 在「串聯多個 Skill 完成一個完整任務」→ Playbook 層

**層次關係：** Playbook 引用 Skill，Skill 引用知識層。執行任務時從 Playbook 開始讀。

## 3  資料夾說明

### 📥  inbox/  —  零摩擦入口
隨手筆記、草稿、未整理的想法。不需要任何格式。  
✦ **使用時機：** 任何你不確定放哪裡的東西，先丟這裡。AI 定期幫你分類。

### 📄  raw/  —  原始素材
文章、影片逐字稿、Podcast 筆記等原始內容。唯讀，不會被修改。  
✦ **使用時機：** 你讀到的好文章、影片的逐字稿。等待正式 Ingest 處理。

### 📎  Clippings/  —  Web Clipper 自動存放
Obsidian Web Clipper 自動儲存的網頁內容。視同 raw/，唯讀。  
✦ **使用時機：** 不需要手動放。瀏覽器 Clipper 自動存入。

### 🗂  projects/  —  專案知識層
每個專案的學習記錄。只記「學到了什麼」，程式碼留在原目錄。  
✦ **使用時機：** 開新專案時建一個子資料夾，用 overview / learnings / extracted 三個檔案記錄。

### 🧠  wiki/  —  主知識庫
蒸餾後的知識頁面，由 AI 維護。所有頁面都有交叉連結。  
✦ **使用時機：** 不要直接在這裡新增沒有來源的頁面。知識要先經過 inbox 或 raw 再升級進來。

### 📐  Templates/  —  頁面範本
各類型頁面的格式範本。參考用，不修改。

### wiki/ 子資料夾一覽

| 資料夾 | 放什麼 | 層次 |
|--------|--------|------|
| `wiki/concepts/` | 原理、理論、定義；跨域綜合分析（type: synthesis） | 知識層 |
| `wiki/tools/` | 工具評估：功能、優缺點、適用場景 | 知識層 |
| `wiki/marketing/` | 行銷知識（框架、策略、SOP）；**平坦結構，同主題 5 頁後 Lint 提議分資料夾** | 知識層 / Skill 層 |
| `wiki/ai-workflow/` | AI 工具輔助的執行 SOP（指令性） | Skill 層 |
| `wiki/courses/` | 課程 Marp 投影片（穩定版）；開發草稿放 projects/ | 輸出 |
| `wiki/playbooks/` | 多 Skill 串聯的完整執行流程（Marketing Plugin） | Playbook 層 |
| `wiki/summaries/` | 單一原始素材的萃取記錄（過渡用，ingest 完成後可 archived） | 過渡 |
| `wiki/clients/` | 客戶知識（⚠️ 私人，已加入 .gitignore） | 私人 |
| `wiki/cases/` | 活動覆盤、成功/失敗案例（⚠️ 私人，已加入 .gitignore） | 私人 |

## 4  我要記錄 X，放在哪？

遇到不確定的內容，先問這個問題：

| 這是什麼 | 放哪裡 |
|---------|--------|
| 未整理的想法、不確定放哪裡 | `inbox/` |
| 外部素材原文（文章、影片、Podcast） | `raw/` 或 `Clippings/` |
| 解釋「某個 AI/技術概念是什麼」 | `wiki/concepts/` |
| 評估「某個工具的優缺點/用法」 | `wiki/tools/` |
| 行銷知識（框架、策略、方法論） | `wiki/marketing/`（type: marketing） |
| 行銷 SOP（可重複執行的操作步驟） | `wiki/marketing/`（type: workflow） |
| AI 工具輔助的執行流程 | `wiki/ai-workflow/` |
| 多步驟完整執行流程，有明確輸入輸出 | `wiki/playbooks/` |
| 課程投影片（穩定版） | `wiki/courses/` |
| 某個專案中學到的東西 | `projects/[slug]/learnings.md` |

💡 **原則：不確定放哪裡，永遠先放 `inbox/`。**

## 5  Playbook 使用方式

Playbook 是這個系統最強的功能：把你累積的 skill know-how 組合成可直接執行的完整流程。

### 執行 Playbook 的流程

1. 你說：「執行 [playbook 名稱]，輸入是 ___（campaign brief / 素材 / 資料）」
2. LLM 讀取 `wiki/playbooks/[name].md`
3. 按照 Playbook 的 Step 1、2、3… 依序執行，遇到細節去讀對應的 Skill 頁
4. 輸出每個 Step 的產出，確認後繼續下一步
5. 把這次執行的學習記錄進 `projects/[slug]/learnings.md`

### 新增 Playbook 的時機

當你發現同樣的「多步驟流程」重複跑了 2 次以上，就值得建成 Playbook。

### Skill 放哪裡（Playbook 的元件）

| Skill 類型 | 例子 | 放哪裡 | Type |
|-----------|------|--------|------|
| 工具無關的行銷流程 | 競品分析、創意發想框架 | `wiki/marketing/` | workflow |
| AI 工具輔助流程 | 用 Claude 生廣告圖、AI 輔助分析 | `wiki/ai-workflow/` | ai-workflow |

💡 **規則：** Skill 放 domain 資料夾，Playbook 只做編排，不重複寫 Skill 細節——用連結引用即可。

## 6  使用流程（五個 Phase）

### Phase 0  ·  Inbox Triage  —  整理 inbox
**觸發方式：** 你說：「整理 inbox」

- 丟掉：沒有知識價值的筆記
- 移到 raw/：有價值的原始素材，等待日後 Ingest
- 觸發 Phase 1：內容完整的直接進行完整 Ingest

📌 **頻率：** 累積 5 則以上 inbox 筆記時，或每週一次

---

### Phase 1  ·  Ingest  —  讓 AI 處理新素材
**觸發方式：** 你說：「處理這個」/ 「整理這份」

1. AI 讀取素材
2. 在 `wiki/summaries/` 建立素材萃取頁（記錄這份素材說了什麼）
3. 根據內容更新或新增對應的知識頁（`concepts/`、`tools/`、`marketing/`、`ai-workflow/`）
4. 建立雙向交叉連結
5. 更新 `index.md` 和 `log.md`

📌 **一次 Ingest 通常觸及 5–15 個 wiki 頁面**

---

### Phase 2  ·  Compile  —  把好的回答存回 wiki
**觸發方式：** 對話中發現有價值的答案時

任何未來會再次用到的答案，都要存回 wiki。格式可以是：Markdown 頁面、Marp 投影片、比較表格、Playbook。

📌 你說：「把這個存回 wiki」或 AI 主動詢問

---

### Phase 3  ·  Query  —  查詢知識庫
**觸發方式：** 你有問題要問

1. AI 先讀 `index.md` 找相關頁面
2. 讀取相關 wiki 頁面，綜合回答，附引用連結
3. AI 主動詢問：這個答案要存回 wiki 嗎？

📌 Query 之後通常會觸發 Compile

---

### Phase 4  ·  Lint  —  定期健康檢查
**觸發方式：** 你說：「整理一下」/ 「lint」

- 🔴 矛盾：頁面間衝突的資訊
- 🔴 孤立頁面：沒有任何連結指向的頁面
- 🟡 過時內容：被新素材推翻的舊觀點
- 🟡 缺失交叉連結：應該互相引用但沒有的頁面
- 🟢 缺失頁面：被提及但尚未建立的概念
- 🟢 **marketing/ 分叉候選：** 同一個 tag 在 marketing/ 下出現 5 頁以上 → 提議建立子資料夾（等確認後才執行）

📌 **頻率：** 每 2–4 週一次，或 wiki 頁面超過 20 頁後開始

## 7  頁面成熟度（status 欄位）

| Status | 含義 | 引用時注意 |
|--------|------|-----------|
| `inbox` | 隨手記，未驗證，可能不準確 | ⚠️ 不建議直接引用 |
| `draft` | 有結構但尚未完整 | 🟡 可引用但需確認 |
| `growing` | 持續有新資訊進來，動態更新 | 🟡 主流內容可信，細節持續更新 |
| `stable` | 很少變動，高可信度 | ✅ 可直接引用 |
| `archived` | 過時但保留參考 | 🔴 注意時效，勿直接引用 |

## 8  快速指令參考

| 你想做什麼 | 跟 Claude 說 |
|-----------|-------------|
| 丟入隨手筆記 | 直接丟在對話，或存成檔案放 inbox/ |
| 處理一篇文章 / 影片 | 「處理這個」/ 「整理這份」 |
| 清空 inbox | 「整理 inbox」 |
| 執行完整行銷流程 | 「執行 [playbook 名稱]，輸入是 ___」 |
| 查詢知識庫 | 「wiki 裡有沒有關於 X 的內容？」 |
| 存回好答案 / 建 Playbook | 「把這個存回 wiki」 |
| 健康檢查 | 「lint」/ 「整理一下」 |
| 開新專案知識記錄 | 「在 projects/ 幫我開 [slug] 的資料夾」 |
| 查看目前有哪些頁面 | 「讀一下 index.md」 |
